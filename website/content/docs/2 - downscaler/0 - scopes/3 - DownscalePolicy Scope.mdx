# DownscalePolicy Scope

The **DownscalePolicy Scope** is the fourth scope available and holds configurations set by a `DownscalePolicy` resource.
It overrides values already defined inside the [Default Scope](ref:docs-default-scope),
[ENV Scope](ref:docs-env-scope) and [CLI Scope](ref:docs-cli-scope),
but values defined inside the DownscalePolicy scope can be overridden by the [Namespace Scope](ref:docs-namespace-scope)
and the [Workload Scope](ref:docs-workload-scope).
It is only used to set values.

<HierarchyDiagram highlight="f" />

A `DownscalePolicy` is a namespaced custom resource.
It lets users who only have permissions inside their own namespace define scaling values for some or all of their workloads,
without annotating the `Namespace` object or every single workload.
Since it is a dedicated resource, access to it is controlled by standard Kubernetes RBAC.

:::info[Enabling the DownscalePolicy Scope]

The DownscalePolicy scope is disabled by default.
It can be enabled by setting the [`downscalePolicy.enabled`](ref:docs-helm-downscale-policy) value of the Helm Chart to `true`,
which sets the [`--downscale-policy`](ref:docs-runtime-configuration#downscale-policy) runtime configuration.
The `DownscalePolicy` CRD is installed by the Helm Chart.

:::

## Values

At the DownscalePolicy Scope, the following [values](ref:docs-values) can be configured in the `spec` of the resource.
They use the same syntax as the corresponding annotations.

- `downscalePeriod`: [downscaler/downscale-period](ref:docs-values#downscale-period)
- `downtime`: [downscaler/downtime](ref:docs-values#downtime)
- `upscalePeriod`: [downscaler/upscale-period](ref:docs-values#upscale-period)
- `uptime`: [downscaler/uptime](ref:docs-values#uptime)
- `exclude`: [downscaler/exclude](ref:docs-values#exclude)
- `excludeUntil`: [downscaler/exclude-until](ref:docs-values#exclude-until)
- `forceUptime`: [downscaler/force-uptime](ref:docs-values#force-uptime)
- `forceDowntime`: [downscaler/force-downtime](ref:docs-values#force-downtime)
- `downscaleReplicas`: [downscaler/downscale-replicas](ref:docs-values#downscale-replicas)
- `gracePeriod`: [downscaler/grace-period](ref:docs-values#grace-period)
- `scaleChildren`: [downscaler/scale-children](ref:docs-values#scale-children)
- `upscaleExcluded`: [downscaler/upscale-excluded](ref:docs-values#upscale-excluded)

:::warning

Some values are incompatible with others.
You can check their compatibility by viewing the dedicated documentation page from the list above.

:::

## Usage

```yaml title="office-hours.yaml"
apiVersion: kube-downscaler.io/v1alpha1
kind: DownscalePolicy
metadata:
  name: office-hours
  namespace: team-a
spec:
  # optional: explicit workloads in the namespace of the policy
  targetRefs:
    - group: apps
      kind: Deployment
      name: api
  # optional: matches current and future workloads
  selector:
    # optional: omitted means all kinds the downscaler targets
    kinds:
      - group: apps
        kind: StatefulSet
    # optional: standard label selector (matchLabels / matchExpressions)
    matchLabels:
      tier: backend
  uptime: "Mon-Fri 08:00-19:00 Europe/Paris"
  downscaleReplicas: "1"
  gracePeriod: "15m"
```

```bash
kubectl apply -f office-hours.yaml
kubectl get downscalepolicies -n team-a
```

### Targeting

A workload is matched by a policy if it is listed in `targetRefs` **or** matches the `selector`.
If both `targetRefs` and `selector` are omitted, the policy matches every workload in its namespace.

- `targetRefs` lists workloads by `group`, `kind` and `name`.
  Use an empty `group` for the core API group (e.g. `Service`).
- `selector` matches workloads of the listed `kinds` (all kinds if omitted) whose labels match `matchLabels` and `matchExpressions`.
  When both are set, a workload has to match both the kind and the labels.

Only workloads the downscaler is configured to handle with [`--include-resources`](ref:docs-runtime-configuration#include-resources)
can be matched.

### Conflicts

If several policies match the same workload, only one of them is applied:
the policy with the oldest `creationTimestamp` wins.
On a tie, the first policy in alphabetical `namespace/name` order wins.
This follows the conflict resolution of the [Gateway API policy attachment](https://gateway-api.sigs.k8s.io/geps/gep-713/).

The policies that lose get an `Accepted=False` condition with the reason `Conflicted`, listing the affected workloads.

### Status

The downscaler reports the result of each scan in the `status` of the policy.
The status is only written when it changes.

| Field / Condition    | Description                                                                                 |
| -------------------- | ------------------------------------------------------------------------------------------- |
| `Valid` condition    | `True` if all values were parsed successfully, `False` with reason `InvalidValue` otherwise |
| `Accepted` condition | `False` with reason `Conflicted` if another policy wins on some matched workloads           |
| `matchedWorkloads`   | The amount of workloads the policy is applied to                                            |
| `workloads`          | The workloads the policy is applied to, sorted by group, kind and name (at most 50)         |
| `observedGeneration` | The generation of the policy that was last evaluated                                        |

If a policy is applied to more than 50 workloads, only the first 50 are listed in `workloads`,
while `matchedWorkloads` always holds the total amount.

Invalid values also create an event on the policy, and invalid policies are not applied.

## Permissions

Users need permissions on the `downscalepolicies` resource of the `kube-downscaler.io` group to manage policies.
This can be granted per team with a namespaced `Role`, which allows cluster administrators to decide which teams may define schedules.

Alternatively, setting the [`downscalePolicy.aggregateToDefaultRoles`](ref:docs-helm-downscale-policy) value of the Helm Chart to `true`
grants these permissions to every user bound to the default `admin`, `edit` and `view` ClusterRoles.
